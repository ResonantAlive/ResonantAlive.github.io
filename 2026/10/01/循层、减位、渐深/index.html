循层、减位、渐深

我们很高兴开源 RDT-Solmen-120M 的完整训练包。仓库其实五月底就已经放到 GitHub 上了，这篇算是补一个正式的介绍。

一句话概括：单卡、2B tokens、50 元以内，从原始 jsonl 一路训练到一个能对话的 120M 中文小模型。

一本书读一遍和读四遍，书还是那本书，读四遍的人通常理解得更深。循环深度 Transformer（Recurrent-Depth Transformer，下文简称 RDT）做的就是这件事：同一组层，让数据反复过几遍。参数量不变，模型”想”的时间变长了。

整条流水线：

原始 jsonl → 预分词 → 显存测试 → A/B/C/D/E 五阶段预训练 → SFT → 自我认知校准 → 对话

为什么？

小模型的参数预算非常紧。以我们的配置为例，122.3M 参数里，embedding 一项就占了约 54.7M，接近一半。真正负责”思考”的 Transformer 层只有约 67.6M。

想让模型更聪明，常规做法是加宽或者加深，但这两条路都要加参数，显存和 optimizer states 也跟着一起涨。

我们没有去堆更多的层，而是把现有的 6 层循环使用：训练到最后，每个 token 要过 4 圈，相当于 24 层的计算深度，参数量还是 6 层的。

当然，计算不是白来的。同样训练 2B tokens，RDT 的计算量大约是普通 Dense 的 1.93 倍。所以剩下的问题就是：多出来的这部分算力，怎么再省回来？

我们的回答就是标题里的三件事：

  • 循层：一组层跑多圈，用计算换参数。
  • 减位：Linear 走 Transformer Engine 的真 FP8，算得更快。
  • 渐深：seq_len 和 depth 从小到大交错生长，前期少花钱。

How to work？

循层：6 层真实参数，跑 4 圈

前向的核心逻辑只有几行（简化版）：

把同一组层反复跑，最怕的是越跑越飘：圈数一多，隐状态就容易漂移，训练跟着不稳。为此我们做了三处处理：

每一圈都重新注入输入。 进入新的一圈之前，旧状态先乘一个 sigmoid 衰减，再加上经过 tanh 门控的原始 embedding。两个系数都按维度可学习，而且都有界：初始时旧状态保留一半，输入门控约为 0.1。

残差按圈数缩放。 每个 block 的残差分支先乘 1/sqrt(圈数)，再乘一个可学习的门，门的取值被限制在 (0, 2) 之间，初始为 1。圈数变多时，单圈的更新幅度会自动变小。

RoPE cache 保持 FP32。 只在 forward 时把当前用到的 slice 转成计算精度，避免长上下文的相位精度被永久降级。

其余结构都很常规：

项目 值
参数量 约 122.3M（embedding 约 54.7M）
d_model 1024
注意力 GQA，16 个 Q head / 4 个 KV head
真实层数 6
FFN SwiGLU，hidden 2816
归一化 / 位置编码 RMSNorm / RoPE（base 500000）
词表 53376，tie embeddings
上下文 2048
训练深度 2 → 3 → 4

减位：真 FP8，而不是模拟出来的 FP8

打开 --use_fp8_linears 后，QKV/O 投影和 Dense SwiGLU FFN 全部换成 NVIDIA Transformer Engine 的 FP8 Linear，recipe 是 HYBRID：forward 用 E4M3，backward 用 E5M2。

不是所有东西都适合 FP8。RMSNorm、attention softmax、loss 和 optimizer states 都保留高精度，只让矩阵乘这种最吃算力、也最扛得住低精度的部分走 FP8。

注意力优先走 FlashAttention2，没装的话退回 PyTorch SDPA。没装 Transformer Engine 时，脚本会自动关掉 FP8 Linear、退回 BF16，并打印警告：能跑，但会明确告诉你现在跑的不是 FP8。

渐深：seq 和 depth 交错生长

训练前期，模型连基本的语言规律都还没学会，这时候就上长序列、深循环，很多算力是浪费的。所以我们把 2B tokens 拆成五个阶段：

Stage Token 进度 seq_len depth 每 token 训练计算量 约 step 数
A 0%–35% 512 2 1.22 GFLOPs 2,670
B 35%–50% 1024 2 1.29 GFLOPs 1,144
C 50%–70% 1024 3 1.77 GFLOPs 1,526
D 70%–75% 2048 3 2.00 GFLOPs 381
E 75%–100% 2048 4 2.56 GFLOPs 1,907

depth 走的是 2+1+1，seq_len 从 512 长到 2048，两者交错增长，不在同一个边界同时增加。

每个阶段单独启动一个进程，阶段内 shape 固定，方便 CUDA kernel 复用；下一阶段自动从最新 checkpoint 恢复。run_2b_train.sh 会顺序跑完 A 到 E，不需要手动切换。

和全程 seq 2048、depth 4 相比，这套 schedule 把总计算量从约 5.11 EFLOPs 压到约 3.42 EFLOPs，省下大约三分之一。

MTP 去哪了？

仓库名里写着 MTP，但它默认是关的。

独立的 MTP head 是一个 d_model × vocab_size 的输出头，会额外增加约 54.7M 参数，120M 的模型一下子就变成 177M。按当前 schedule 粗略估算，训练计算量还要再涨 18% 左右，optimizer states 也要多占一份显存。

为了让总参数量留在 120M 附近，我们默认把它关掉了。代码路径保留着，传 --mtp_weight > 0 就会启用。

算一笔账

项目 数值
训练 tokens 2B
每个 optimizer step 262,144 tokens
optimizer steps 约 7,630
总计算量 约 3.42 EFLOPs
相对普通 depth=1 Dense 约 1.93×

按脚本默认的 --peak_tflops 419 估算，MFU 在 20% 时大约需要 11.3 小时，25% 时大约 9.1 小时。租一张 RTX 5090，整套流程能控制在 50 元以内。

实际时间以训练日志里的 tok/s 为准，日志会直接打印 ETA。训练开始后，也可以用 python speed_estimate.py --tok_s <实测值> 重新估一次。

不知道写什么标题

torch.compile 默认关闭。 PyTorch 2.8 的 CUDA Graph 捕获会和 RDT 的循环复用冲突。想试编译可以用 USE_COMPILE=1 COMPILE_MODE=default，但不要打开 COMPILE_CUDAGRAPHS=1。

显存测试要算全。 memory_test.py 会在目标 GPU 上测出 seq_len 为 512/1024/2048、depth 为 4 时的最大安全 micro batch。测量范围包括 activation、gradient、AdamW optimizer states 和 optimizer.step 的峰值，结果写进 config.txt 供训练脚本读取。每步 tokens 固定为 262,144，batch 越大，梯度累积的步数就越少。

gradient checkpointing 不主动开。 它会拖慢速度，只有显存测试 OOM 时才由脚本自动启用。

数据按块懒加载。 训练数据不会在启动时一次性读进内存，而是按 64MB 的块做 LRU 缓存。90GB 内存的服务器默认给 60GB 缓存，预分词和数据预取各用 15 个 worker。

尽量不让 GPU 等 CPU。 逐 micro-step 的 loss 同步检查默认关闭；排查 NaN 时再加 --loss_finite_check_every 1。

weight decay 只给矩阵。 AdamW（优先 fused）只对矩阵权重做 weight decay，RMSNorm、门控、衰减这类一维参数不做。

中断也会存档。 默认每 1000 step 保存一次，只保留最近 3 个。按 Ctrl+C 或异常退出时，脚本会先尽量保存 checkpoint 再退出。checkpoint 是 Hugging Face 风格的目录，latest.json 指向最新一份。

QA

  1. 推理时 depth 能改吗？
    能。Infer.py 和 InferSFT.py 都有 --depth 参数，默认是 4，也就是训练最后阶段用的深度。depth 只决定”想几圈”，不改变参数量；每多一圈，每个 token 的计算量就多一份。你可以拿同一个 checkpoint 跑 1 到 4 圈，自己对比效果。
  2. 没有 RTX 5090，或者装不上 Transformer Engine，能跑吗？
    能。没有 Transformer Engine 会自动退回 BF16 Linear，没有 flash-attn 会退回 PyTorch SDPA，只是慢一些。H800 推荐 CUDA 12.8 + BF16/FP8 路线。5090 是 Blackwell 架构（sm_120），PyTorch、flash-attn、Transformer Engine 的 wheel 都要支持 sm_120。环境往往是最容易卡住的一步，推荐直接用 NVIDIA 的 PyTorch NGC 容器。
  3. 为什么是 122.3M，不是 120M？
    embedding 占了大头。如果一定要压到 120.0M，可以继续调小 ffn_hidden_size，或者改词表和输出头策略。estimate_params.py 可以直接打印当前配置的参数量。
  4. Windows 能用吗？
    训练请用 Linux，Transformer Engine 只在 Linux 下安装。训练好的 checkpoint 可以拷回 Windows，用 InferSFT.py 或 ChatSFT.py 在本机对话。

已知限制

  • 只支持单卡。 训练脚本目前没有 DDP / FSDP。
  • torch.compile 默认关闭。 受 CUDA Graph 冲突影响，编译带来的那部分加速暂时拿不到。
  • 参数量是 122.3M，不是严格的 120M。
  • MTP 默认关闭。 开启后参数量和计算量都会明显上涨。
  • 还没有公开的基准评测。 仓库里目前只有生成和对话测试脚本。
  • 主要面向中文。 预训练默认数据是 CCI3-HQ，SFT 可以按比例混入英文数据。
