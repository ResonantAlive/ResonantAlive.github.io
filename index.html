识迹、衡文、知学

我们很高兴开源 writing_modify，这是我们开源的第 12 个项目。
选择题有标准答案，对就是对，错就是错：一位老师一小时能批完 200 份选择题，却往往批不完 20 份作文。
原因在于作文是主观的。主观意味着评分会受老师的评分风格、当天的心情，甚至疲劳程度影响：同一位老师上午和深夜的尺度可能不一样，不同老师之间差异更大。批得慢，结果也不一定好。
我们的解决方法：用 few-shot 让模型学会”你的”尺度
我们没有去训练或微调模型，而是采用 few-shot（少样本学习）：
老师先认真批改 5～10 份作文：打分，也可以写意见条目；
系统把这些复核过的作文作为示范放进提示词（默认每次最多 3 份，可配置）；
大模型按同样的尺度批改其余作文；
老师只需复核：一键采纳 AI 的结果，或者改分、补充意见。改过的结果会成为之后批改的新示范。
整个过程低成本、无需训练，换一批题目、换一位老师马上就能用。示范默认只取自你自己的批改，不会混入别人的数据。在示范和大模型本身能力的加持下，批改结果更稳定、更一致，老师可以把时间花在真正需要判断的作文上，而不是逐份从头批。
一条完整的流水线
上传作文照片 → 分成一篇篇作文 → 识别手写 → 大模型批改 → 老师复核 → 批次汇总与共性问题报告 → 通过 API 接入你的系统
功能一览
两条识别路线：本地 OCR（PP-OCRv6，手写识别在你自己的机器上，只把文字发给大模型，不发照片），或者让视觉模型直接看图。
答题纸模板：先上传同款空白答题纸，系统记住纸上的印刷内容（标题、页边提示、条形码、页码），识别作文时自动去掉，不会混进作文里。
保留学生的拼写错误：识别不会替学生”改对”，这对批改语言分很重要。
批量处理，可暂停、可恢复：失败比例过高或接口连续出错时自动暂停，不会把整批作文白白烧掉。
教师复核：一键采纳、改分、写意见条目；每次修改都新增一版历史，旧版本和 AI 的原始结果不会被覆盖。
批次汇总和共性问题报告：见下面的 QA。
数据留在自己手里：批改数据都是磁盘上的普通文件（JSON 加原图），API key 只保存在服务器上；账号之间严格隔离，别人的数据一律访问不到；默认只监听本机。
QA

  1. 看不到学生的闪光点和整体共性错误怎么办？
    我们在设计时考虑到了这点，并把它加进了 v1：
    每篇作文的批改结果里有判据和评语。想要单篇的闪光点，可以在提示词模板里要求模型写出来。
    批次完成后，可以一键生成”共性问题报告”：汇总全班集中出现的问题（几篇出现、典型表现、涉及哪几篇）、给老师的讲评建议，以及整体优点。
    生成报告只发送题目、评分标准和各篇的评价文字，不发送作文原文和照片。
  2. 我已经有了相关工作台，或者其他 AI 写的软件了，怎么把 writing_modify 的批改数据接入进去？
    我们采用”万物 API”的设计：writing_modify 自己的前端用的就是同一套 REST API（/api/v1）。每个账号都可以签发自己的 API 令牌（Bearer），令牌的权限不会超过账号本身。用它就能上传作文、创建批次、读取批改结果、提交复核。
    批改数据也是磁盘上带版本号的 JSON 文件（复核记录、批次汇总、共性报告），可以直接读取。所以你只需要改动现有工作台的一小部分代码，就能把 writing_modify 合并进你的工作流。
  3. 我的数据会被发到哪里？
    本地 OCR 路线只会把识别出的文字发给你选择的大模型服务商，不发照片；视觉路线会发送照片。服务商是你自己配置的。如果它不是本机地址，第一次使用前系统会要求你明确确认。本软件不会自动向我们上传任何数据。
  4. 批改得准吗？
    结果取决于你选的模型和你给的示范质量。每篇作文会同时记录 AI 分和老师最终分，批次汇总里有两者的平均差，你可以用自己的数据来检验，再决定放手到什么程度。
    下一步：训练本地小模型（完全自愿，欢迎贡献）

DeepSeek-Harness-Distiller-V1.0

开源 DeepSeek-Harness-distiller：为 Agent 训练数据而生的教师模型轨迹蒸馏

我们很高兴开源 DeepSeek-Harness-distiller。这是我们为接下来Cealum系列最大最强模型所开发的Agent蒸馏工作流。

本项目基于 DeepSeek-Harness，修改了部分代码，为 Linux 环境做了部分适配。在原版之上，我们加了一套完整的「教师模型轨迹蒸馏」能力：让强模型在真实任务里自己干活，把整个过程安全、可追溯地录下来，最后产出一份带标签、可直接用于训练的数据集。

为什么？

想蒸馏一个 Agent，光有对话记录是不够的。我们很难知道：

  • 任务到底成功了没有？ 需要客观的判定。
  • 命令执行的结果是什么？ 模型看到的是一段合并后的文本，但数据集需要机器可读的退出码、分离的 stdout/stderr，以及进程是否被信号终止。
  • 录下来的东西能安全落盘吗？ 密钥、令牌不能进入数据集。

并且，让一个仅仅几B参数量的模型通过RL自己发掘正确的道路是非常困难的，算力开销很容易就达到研究员无法承受的程度

因此，蒸馏便成为最好的选择。

How to work？

整套能力由五个新包和一个新应用组成。

五个包（packages/distill/）

包 职责
redaction 落盘前把密钥替换为占位符，覆盖原文、blob、轨迹和归档会话
teacher-lock 在加载时拒绝任何可能服务非锁定模型的组合
trajectory-events 订阅会话与流事件，写出脱敏的原始事件日志和内容寻址的 blob
distill 加载任务定义、运行独立尝试、客观判定、写出带标签的数据集
resource 探测容器实际允许的 CPU/内存，拒绝装不下的切分方案

一个应用（apps/distill/）

  • composition.ts：通过 Cordis Loader 组装，而不是手搭插件
  • agent-runner.ts：生产级 AgentRunner，负责建会话、发消息、带超时地等待空闲、落盘
  • bin.ts：命令行入口，包含参数解析、限流、资源校验和逐任务执行

启动方式是一个新的 profile：dsh --profile distill。

改动

改核心代码是有风险的，所以…

原版手写源码只改了 6 个文件、约 120 行，全部是加法，没有删除，也没有改变原有行为。

  1. llm/src/types.ts：给流式协议的 usage 分片加了可选字段 servedModel，用来记录实际服务请求的模型。
  2. llm-deepseek/src/translate.ts：原版把响应里的 message.model 丢掉了，我们把它读出来并透传。这是上一条的数据来源，只有适配器知道这个信息，插件层拿不到。
  3. tool-bash 和 tool-pwsh：新增 presentationMeta 投影，把退出码、信号、超时、分离的 stdout/stderr 等结构化信息写入模型不可见的工具结果元数据。ToolResult.meta 是框架已有字段，所以不改模型输入，也不会触发快照变更。
    两个都要改，是因为真实 API 测试暴露了一个问题：模型在 Windows 上用的是 pwsh。只改 bash 的话，Windows 主机上的终止信息采集会全部为空。
  4. app-boot/src/index.ts：把 distill-teacher-lock 加入「必须成功启动」名单。教师锁拒绝启动时，应用必须停机，否则会录出一整份归属错误的轨迹。我们的原则是：配置错误要大声失败，而不是静默跳过。
  5. app-boot/src/profile.ts：注册 distill profile。

另有两个生成产物（Cordis 服务目录和插件包清单），由生成器重跑，无需手改。

除此之外，所有能力都以新增插件的方式实现。

不知道写什么标题

教师锁在加载期生效。 它不是运行时的软检查，而是在启动装配里强制：不确定能保证是锁定模型，就不启动。

先脱敏，再落盘。 脱敏覆盖原文、blob、轨迹与归档会话。

判定是客观的。 任务的判据由任务定义给出。为了防止作弊，我们在运行前后对判据做指纹比对，篡改会被发现。

资源切分基于真实限制。 resource 包探测的是容器实际允许的 CPU 和内存，而不是宿主机的数字，装不下的切分方案会被直接拒绝。

验证情况

项目 结果
文档门禁 pnpm run doc-sync 43 / 43 通过

真实 API 的三个用例覆盖了三类结果：判定成功、判定永不通过、预算超限。

快速上手

有一点需要注意：应用运行的是 lib/ 产物，修改 src/ 后需要先执行 pnpm run build:lib:host 重新构建，真实链路才会生效。

已知限制

  • 判据进程没有独立沙箱。 评估器与 runner 同进程，防作弊依赖指纹比对，能发现篡改，但没有进程隔离。
  • thinking 开关尚未记录。 它位于适配器的线格式中，不在 LlmCallConfig 里。目前轨迹记录的是 reasoning_available，即是否实际拿到了思考内容。
  • 尚未实现： 会话日志的脱敏销毁、崩溃恢复、配置优先级链。

Caelum Ouzel : 分星、积云、循轨

我们很高兴开源 Caelum Ouzel（苍穹乌鸫） 的训练代码。这是一个紧凑型 decoder-only MoE（混合专家）语言模型：总参数约 17 亿，每个 token 只激活约 3.5 亿。

你也可以：总成本 200～300 元，从零训练一个属于自己的家庭小模型。实际花费取决于训练时的 MFU、GPU 型号和租卡单价。

仓库：https://github.com/ResonantAlive/Cealum-Ouzel （Apache-2.0）

两三百块，真的够吗？

我们算一笔账。

README 里预训练的默认预算是 20 亿（2B）token。在 RTX PRO 6000 上，FP8 路径实测吞吐约 4.57 万 tok/s（原生 BF16 约 4.27 万）。2B ÷ 45.7k ≈ 43,800 秒，也就是 12 小时出头；再加上编译、验证和存 checkpoint 的开销，乘以你租卡的小时单价，就是总成本的大头。

不想自己算？train.py 可以直接按预算反推要训多少 token：

公式很朴素：（预算 − 预留）÷ 单价 × 3600 × 实测吞吐 × 0.95（安全系数）。

有两点需要注意：

  • 这三个参数必须一起给。
  • 吞吐请填端到端实测值（包含验证、存档、编译和数据等待），不要填纯计算的 tok/s。否则算出来的 token 数偏多，钱花完了，训练还没跑完。不放心的话，可以再加一个 --max-wall-hours 兜底。

开源了什么？

开源：

  • 预训练源码（含 CPT 持续预训练）
  • SFT pipeline
  • DPO 源码
  • tokenizer 训练源码
  • 环境检查、benchmark 与测试
  • 数据集来源 / 推荐数据集

不开源：

  • GRPO 源码、PPO 训练源码
  • DPO 数据集、部分 SFT 数据集
  • 预训练 code 数据集
  • 模型权重与 checkpoint（训练进行中）

按 README 走，大概率可以复现 base 模型。复现不出来先别急着怪代码：训练本身是概率过程，FP8 的精度本来就差，换张卡、换个驱动，曲线都可能有出入。（作者不保证复现结果）

设计要点

文档打包，但不串门。 预训练把多篇文档打包进同一条序列，减少 padding 浪费；同时用 FlashAttention 2 的 varlen 接口，保证注意力不会跨文档。

断点续训精确到 token。 checkpoint 同时保存采样器状态和随机数状态。--resume 之后从上次的位置接着读，不重不漏。

不保存完整 logits。 用 Liger 的分块 linear cross-entropy 计算 32K 词表投影，不需要保存一整块 [tokens, vocab] 的 logits 张量。

FP8 可选，BF16 兜底。 默认走 NVIDIA Transformer Engine 的 FP8（DelayedScaling）；遇到不支持的环境，加 --no-fp8 --no-te 回退原生 BF16。

序列长度逐步拉长。 预训练按 512 → 1024 → 2048 分三段增加序列长度，32K 长上下文交给 CPT 阶段。

后训练也要省显存。 SFT 只监督 assistant 片段；DPO 只预计算一次冻结参考模型的 log-prob，并按参考模型哈希缓存，不用全程再驻留一份 1.7B 的参考模型。

花钱之前先体检。 check_environment.py --strict --full-model 会在付费训练前检查一遍 CUDA、FlashAttention 和 TE，并按正式模型形状跑数值与反向检查。

实时面板。 默认在 http://127.0.0.1:6006 异步绘制 Loss、Val Loss、PPL 与 Val PPL，不占用 CUDA stream。

不建议的做法

1. 拿中文为主的 tokenizer 去处理英文。 分词器的压缩率受主训练语言影响很大。按我们的语料训练出来的 tokenizer，中文平均每个 token 能装下 1.5～2.5 个汉字；英文却可能要 3～5 个 token 才能拼出一个单词，模型处理英文的能力会大幅下降。如果你主要处理英文，建议用 train_tokenizer.py 重新训练一个适配英文的 tokenizer。

2. 买付费数据集。 模型太小了，付费数据集带来的提升很有限。

3. 直接复用大模型的 tokenizer。 embedding 会吃掉大量参数：以 15 万词表、1024 隐藏维度为例，光 embedding 就约 1.5 亿参数，接近我们每个 token 激活参数（3.5 亿）的一半，而 32K 词表的 embedding 只有约 3,355 万。留给 Transformer block 的参数变少，模型能力下降。同时 logits 也跟着放大近 5 倍，显存吃紧只能把 micro batch 调小，tensor 喂不满，MFU 下降，训练变慢。

4. 做 logits / 隐状态蒸馏。 需要和教师模型使用同一个 tokenizer、相同的超参数，门槛较高。

5. 接入 Agent 工具。 模型的工作记忆连 system prompt 都不一定能完整存下，极易出错，甚至造成实际损失。而且说实话，你觉得 1.7B 能有多少指令遵循能力？

循层、减位、渐深

我们很高兴开源 RDT-Solmen-120M 的完整训练包。仓库其实五月底就已经放到 GitHub 上了，这篇算是补一个正式的介绍。

一句话概括：单卡、2B tokens、50 元以内，从原始 jsonl 一路训练到一个能对话的 120M 中文小模型。

一本书读一遍和读四遍，书还是那本书，读四遍的人通常理解得更深。循环深度 Transformer（Recurrent-Depth Transformer，下文简称 RDT）做的就是这件事：同一组层，让数据反复过几遍。参数量不变，模型”想”的时间变长了。

整条流水线：

原始 jsonl → 预分词 → 显存测试 → A/B/C/D/E 五阶段预训练 → SFT → 自我认知校准 → 对话

为什么？

小模型的参数预算非常紧。以我们的配置为例，122.3M 参数里，embedding 一项就占了约 54.7M，接近一半。真正负责”思考”的 Transformer 层只有约 67.6M。

想让模型更聪明，常规做法是加宽或者加深，但这两条路都要加参数，显存和 optimizer states 也跟着一起涨。

我们没有去堆更多的层，而是把现有的 6 层循环使用：训练到最后，每个 token 要过 4 圈，相当于 24 层的计算深度，参数量还是 6 层的。

当然，计算不是白来的。同样训练 2B tokens，RDT 的计算量大约是普通 Dense 的 1.93 倍。所以剩下的问题就是：多出来的这部分算力，怎么再省回来？

我们的回答就是标题里的三件事：

  • 循层：一组层跑多圈，用计算换参数。
  • 减位：Linear 走 Transformer Engine 的真 FP8，算得更快。
  • 渐深：seq_len 和 depth 从小到大交错生长，前期少花钱。

How to work？

循层：6 层真实参数，跑 4 圈

前向的核心逻辑只有几行（简化版）：

把同一组层反复跑，最怕的是越跑越飘：圈数一多，隐状态就容易漂移，训练跟着不稳。为此我们做了三处处理：

每一圈都重新注入输入。 进入新的一圈之前，旧状态先乘一个 sigmoid 衰减，再加上经过 tanh 门控的原始 embedding。两个系数都按维度可学习，而且都有界：初始时旧状态保留一半，输入门控约为 0.1。

残差按圈数缩放。 每个 block 的残差分支先乘 1/sqrt(圈数)，再乘一个可学习的门，门的取值被限制在 (0, 2) 之间，初始为 1。圈数变多时，单圈的更新幅度会自动变小。

RoPE cache 保持 FP32。 只在 forward 时把当前用到的 slice 转成计算精度，避免长上下文的相位精度被永久降级。

其余结构都很常规：

项目 值
参数量 约 122.3M（embedding 约 54.7M）
d_model 1024
注意力 GQA，16 个 Q head / 4 个 KV head
真实层数 6
FFN SwiGLU，hidden 2816
归一化 / 位置编码 RMSNorm / RoPE（base 500000）
词表 53376，tie embeddings
上下文 2048
训练深度 2 → 3 → 4

减位：真 FP8，而不是模拟出来的 FP8

打开 --use_fp8_linears 后，QKV/O 投影和 Dense SwiGLU FFN 全部换成 NVIDIA Transformer Engine 的 FP8 Linear，recipe 是 HYBRID：forward 用 E4M3，backward 用 E5M2。

不是所有东西都适合 FP8。RMSNorm、attention softmax、loss 和 optimizer states 都保留高精度，只让矩阵乘这种最吃算力、也最扛得住低精度的部分走 FP8。

注意力优先走 FlashAttention2，没装的话退回 PyTorch SDPA。没装 Transformer Engine 时，脚本会自动关掉 FP8 Linear、退回 BF16，并打印警告：能跑，但会明确告诉你现在跑的不是 FP8。

渐深：seq 和 depth 交错生长

训练前期，模型连基本的语言规律都还没学会，这时候就上长序列、深循环，很多算力是浪费的。所以我们把 2B tokens 拆成五个阶段：

Stage Token 进度 seq_len depth 每 token 训练计算量 约 step 数
A 0%–35% 512 2 1.22 GFLOPs 2,670
B 35%–50% 1024 2 1.29 GFLOPs 1,144
C 50%–70% 1024 3 1.77 GFLOPs 1,526
D 70%–75% 2048 3 2.00 GFLOPs 381
E 75%–100% 2048 4 2.56 GFLOPs 1,907

depth 走的是 2+1+1，seq_len 从 512 长到 2048，两者交错增长，不在同一个边界同时增加。

每个阶段单独启动一个进程，阶段内 shape 固定，方便 CUDA kernel 复用；下一阶段自动从最新 checkpoint 恢复。run_2b_train.sh 会顺序跑完 A 到 E，不需要手动切换。

和全程 seq 2048、depth 4 相比，这套 schedule 把总计算量从约 5.11 EFLOPs 压到约 3.42 EFLOPs，省下大约三分之一。

MTP 去哪了？

仓库名里写着 MTP，但它默认是关的。

独立的 MTP head 是一个 d_model × vocab_size 的输出头，会额外增加约 54.7M 参数，120M 的模型一下子就变成 177M。按当前 schedule 粗略估算，训练计算量还要再涨 18% 左右，optimizer states 也要多占一份显存。

为了让总参数量留在 120M 附近，我们默认把它关掉了。代码路径保留着，传 --mtp_weight > 0 就会启用。

算一笔账

项目 数值
训练 tokens 2B
每个 optimizer step 262,144 tokens
optimizer steps 约 7,630
总计算量 约 3.42 EFLOPs
相对普通 depth=1 Dense 约 1.93×

按脚本默认的 --peak_tflops 419 估算，MFU 在 20% 时大约需要 11.3 小时，25% 时大约 9.1 小时。租一张 RTX 5090，整套流程能控制在 50 元以内。

实际时间以训练日志里的 tok/s 为准，日志会直接打印 ETA。训练开始后，也可以用 python speed_estimate.py --tok_s <实测值> 重新估一次。

不知道写什么标题

torch.compile 默认关闭。 PyTorch 2.8 的 CUDA Graph 捕获会和 RDT 的循环复用冲突。想试编译可以用 USE_COMPILE=1 COMPILE_MODE=default，但不要打开 COMPILE_CUDAGRAPHS=1。

显存测试要算全。 memory_test.py 会在目标 GPU 上测出 seq_len 为 512/1024/2048、depth 为 4 时的最大安全 micro batch。测量范围包括 activation、gradient、AdamW optimizer states 和 optimizer.step 的峰值，结果写进 config.txt 供训练脚本读取。每步 tokens 固定为 262,144，batch 越大，梯度累积的步数就越少。

gradient checkpointing 不主动开。 它会拖慢速度，只有显存测试 OOM 时才由脚本自动启用。

数据按块懒加载。 训练数据不会在启动时一次性读进内存，而是按 64MB 的块做 LRU 缓存。90GB 内存的服务器默认给 60GB 缓存，预分词和数据预取各用 15 个 worker。

尽量不让 GPU 等 CPU。 逐 micro-step 的 loss 同步检查默认关闭；排查 NaN 时再加 --loss_finite_check_every 1。

weight decay 只给矩阵。 AdamW（优先 fused）只对矩阵权重做 weight decay，RMSNorm、门控、衰减这类一维参数不做。

中断也会存档。 默认每 1000 step 保存一次，只保留最近 3 个。按 Ctrl+C 或异常退出时，脚本会先尽量保存 checkpoint 再退出。checkpoint 是 Hugging Face 风格的目录，latest.json 指向最新一份。

QA

  1. 推理时 depth 能改吗？
    能。Infer.py 和 InferSFT.py 都有 --depth 参数，默认是 4，也就是训练最后阶段用的深度。depth 只决定”想几圈”，不改变参数量；每多一圈，每个 token 的计算量就多一份。你可以拿同一个 checkpoint 跑 1 到 4 圈，自己对比效果。
  2. 没有 RTX 5090，或者装不上 Transformer Engine，能跑吗？
    能。没有 Transformer Engine 会自动退回 BF16 Linear，没有 flash-attn 会退回 PyTorch SDPA，只是慢一些。H800 推荐 CUDA 12.8 + BF16/FP8 路线。5090 是 Blackwell 架构（sm_120），PyTorch、flash-attn、Transformer Engine 的 wheel 都要支持 sm_120。环境往往是最容易卡住的一步，推荐直接用 NVIDIA 的 PyTorch NGC 容器。
  3. 为什么是 122.3M，不是 120M？
    embedding 占了大头。如果一定要压到 120.0M，可以继续调小 ffn_hidden_size，或者改词表和输出头策略。estimate_params.py 可以直接打印当前配置的参数量。
  4. Windows 能用吗？
    训练请用 Linux，Transformer Engine 只在 Linux 下安装。训练好的 checkpoint 可以拷回 Windows，用 InferSFT.py 或 ChatSFT.py 在本机对话。
